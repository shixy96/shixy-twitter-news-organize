## 去重与源帖优先

* 以 `_canonical_id` 或 `_canonical_url` 作为同一事件的主键；同一事件只能保留 1 条

* 若源帖和代理帖都存在，优先源帖

* 若 `_source_proxy=true` 且 `_canonical_url` 存在，不要因为它是 quote/retweet 代理就直接丢弃；这代表源帖没被 list 直收录，但事件本身可能重要

* 多人 quote/retweet 同一源帖时，合并为 1 条；主链接用 `_canonical_url`；讨论帖补充链接最多 1 条（优先 `_related_urls` 中高互动帖），但在 `_strong_links` 已有 3 条时不追加

* `likely_reply`、`quoted`、`_related_urls`、`_strong_links`、`_external_links` 都要用于合并和判断同一事件，避免拆成多条、避免丢失源资料链接

### 同一事件多角度合并规则

同一事件（以 `_canonical_id`/`_canonical_url` 或"主题指向同一首发帖"为判断标准）的不同维度分析，**必须合并为 1 条**：

* 技术根因分析、法律/版权分析、社区 fork/二次开发、官方回应等，均属同一事件的不同维度

* 合并时，要点可用分号（`；`）罗列多个维度；主链接用首发帖，补充链接保留最具信息量的 1-2 条分析帖

* **不得**将同一首发事件的多个讨论帖拆为独立条目

独立但表面相似的事件（如不同组织同类型事件、同一话题不同研究团队的论文），必须分别独立成条，禁止在一条中交叉引用另一事件的讨论帖。

### 同项目内容数量限制

* 同一项目（如 OpenClaw）在当天报道中最多出现 **2 次**，无论以何种角度（版本更新、定价、社区讨论等）

* 超出 2 次时，必须合并到已有条目中（不同角度用分号串联）；不得以"不同角度"为借口拆分为独立条目

* 合并后的条目，同一项目的多个角度只占用 1 次计数

### 合并 vs 独立判断决策树

遇到两条内容时，按以下顺序判断：

1. **是否共享** **`_canonical_id`** **或** **`_canonical_url`？** → 是：合并为 1 条
2. **是否源自同一首发帖的二次讨论/分析/回应？**（技术根因、工程解读、版权影响等）→ 是：合并，主链接用首发帖，分析帖作补充链接
3. **是否为不同主体/组织的独立事件，仅恰好同类或同天发生？** → 是：独立成条

具体例子：

* ✅ 合并：「Claude Code 源码泄露首发帖」+ 「dotey 对该泄露的工程分析」= 同一事件，合并

* ✅ 合并：「Claude Code 源码泄露」+ 「Bun bug 根因分析」= 同一事件的技术维度，合并

* ❌ 不合并：「Claude Code 源码泄露」vs「OpenAI Codex 代码库泄露」= 不同主体的独立事件，分别成条

* ❌ 超过 2 次：「OpenClaw v1」「OpenClaw 定价分析」「OpenClaw Claude 封禁」= 同一项目 3 条，选 2 条最重要的保留

## 历史去重

在最终生成 `post.json` 前，检查编排层传入的最近 2 份历史 `post.json`。

* 若同一 `_canonical_id`/`_canonical_url` 已被前一天或前两天覆盖，默认不再入选

* 只有在今天出现明显更强的聚合传播数据，或新增有效信息时，才允许作为 follow-up 再次入选

* 新增有效信息包括：

  * 新的 repo/paper/release/官方回应等第三方资料链接

  * 作者自回复中的正文延续

  * 作者自回复或当天讨论帖里的信息性图片/视频

  * 新 benchmark、新数据、新 release 说明

* 历史命中不仅要看 `_canonical_id/_canonical_url`，也要结合 `_strong_links` / `_external_links` 判断是否其实是同一 paper/repo/release 的后续讨论

* backfill 最多 1-2 条

**backfill 与 follow-up 标注格式**（必须在标题中标注，不得仅在要点或选题价值中提及）：

| 情况                         | 标题格式                  | 说明                                       |
| -------------------------- | --------------------- | ---------------------------------------- |
| 旧帖今日发酵（`_window=backfill`） | `「延迟发酵 {M月D日}」{原始标题}` | 日期取自 `item.time`（UTC+8），如 `「延迟发酵 3月28日」` |
| 今日新帖跟进昨日事件                 | `「跟进」{原始标题}`          | 今天有新内容，不是旧帖本身                            |

## 分类列表（预定义 + 动态补充）

**固定分类**（优先使用，相同内容必须归入相同分类）：

* 模型发布：新模型发布、模型更新、模型架构论文

  * ✅ 包含：新模型权重发布、模型版本更新、模型系列发布

  * ❌ 不包含：源码泄露、代码仓库泄露（归入安全事件）；SDK/工具更新（归入开发生态）

* 开发生态：开发工具、API、SDK、插件、AI coding agent 相关

  * ✅ 包含：SDK 发布、工具链更新、开源项目重大里程碑、编程 agent 功能更新

  * ❌ 不包含：纯模型发布（归入模型发布）；安全事件（归入安全事件）

* 技术洞察：深度技术分析、工程实践、benchmark、学术论文

* 产品动态：产品功能更新、UI 更新、服务策略调整（非模型本身）

**动态分类**（仅在当天有特殊内容时启用）：

* 安全事件：安全漏洞、供应链攻击、数据泄露、**源码/代码库泄露**（即使涉及 AI 公司的模型相关代码）

* 行业观点

**多分类冲突时的优先级**（内容同时符合多个分类时，按此顺序选择）：\
安全事件 > 模型发布 > 开发生态 > 技术洞察 > 产品动态

* 例：新模型同时是新产品 → 模型发布

* 例：源码泄露涉及 AI 公司 → 安全事件（不是模型发布）

* 例：新 SDK 发布但非模型本身 → 开发生态

**禁止使用**以下非标准分类名（即使语义相近也不允许）：\
`开源生态`、`技术研究`、`安全研究`、`安全法律`、`工程突破`、`Dev Ecosystem`、`Model Releases`、`Technical Insights`、`Product Updates`

**规则**：优先使用固定分类；相同类型内容必须归入同一分类。每类选 2-5 条，宁缺毋滥；当天高质量 fresh 很少时，不要拿低质量观点凑数。

整理摘要时突出：为什么值得我关注（技术突破、异常数据、行业风向、延迟发酵）。

### 取舍优先级

* 默认目标 8-12 条

* 当日候选总数 `>= 8` 时，最终入选必须控制在 8-12 条

* 当日候选总数 `< 8` 时，可少于 8 条，但不得超过候选总数

* 优先级从高到低：首发论文/基准 > 官方 docs/blog/release > 开源 release/GitHub > 工程实证/成本研究 > 行业重大事件 > 高信息密度 thread > 纯观点/轻量 workflow

**互动数据参考阈值**（辅助判断，非硬性截止）：

* likes > 5000：强信号，除非内容明显不符主题，否则应入选

* likes 1000–5000：中等信号，需结合内容突破性价值综合判断

* likes 500–1000：弱信号，仅在首发论文/重大 release/首发 benchmark 时可入选

* likes < 500：需极强内容理由才入选（如官方首发 release、重大安全事件等）

* 当研究/工具/源码条目与纯观点竞争时，优先研究/工具/源码；不要用观点贴挤掉 repo/paper/release

* 纯观点类条目（某人对事件的评论/解读，无原始资料链接）最多 2 条，且必须**同时满足**：

  1. 来自关键人物（见关键人物库）或互动显著高（likes > 5000）
  2. 附有原始资料链接（paper/repo/official doc），不得只有 X 帖链接

* 无实证的观点帖（如"某人说 X 是趋势"类）即使高互动也不选入主条目，可作为已入选条目的补充链接

* 若同类事件里已有 repo/paper/release/官方 docs，优先选带原始资料链接的那条

### 弱内容排除（直接排除，不进入候选）

1. **官号自我宣传**：以下情况应排除

   * 官方插件宣传、企业版/Pro 版差异化功能

   * 招聘公告、直播预告、社区活动

   * **以下情况可入选**（不受上述限制）：

     * 全新能力发布（包括 SDK 首次发布、新 API 端点、全新工具）

     * 跨生态动态

     * Breaking Changes

     * 安全/合规事件
2. **数据较旧**：当天新数据极少时才选入前一天的内容，且需标注"延迟发酵"
3. **互动极低**：likes < 500 且 bookmarks < 50 的条目需严格审视
4. **重复事件合并**：

   * 同一事件多人讨论时，合并为 1 条，优先选首发帖

   * 另一条作为补充链接保留
5. **内容核实**：标题或摘要与原文不符的条目应排除；不得脑补内容
6. **与 AI/开发者生态弱相关**：纯 CLI 工具技巧、终端配置、SSH 运维、系统维护等话题，除非有明确的 AI/ML 生态影响（如被 AI 工具引发或对 AI 工具链有直接影响），否则不选入
7. **推测表述为事实**：当原始帖使用"可能""疑似""或为""据推测"等模糊措辞时，本条目标题及要点不得将其改写为确定性结论

### 表述确定性要求

* 当事件分析基于推测而非官方确认时，必须保留原帖的模糊措辞（"或为""可能""据分析""疑似"）

* 禁止将社区推测、技术分析或二手解读表述为已确认事实

* 标题中尤其注意：不得把"X 可能是原因"改写为"X 是原因"或"X 导致了 Y"

### 正文质量要求

* 每条正文必须达到 **80 字符以上**，提供充分背景与数据支撑

* 正文过短（<80 字符）且缺乏实质内容的条目，应降低为补充链接（related_links），不作为独立条目入选

* 正文必须包含"why it matters"框架：解释为什么这条值得读者关注

### 高价值条目第三方链接要求

以下类型条目**必须包含**对应第三方链接，否则不得作为独立条目入选（可降为补充链接）：

| 条目类型 | 必须包含的第三方链接 | 说明 |
| -------- | ------------------- | ---- |
| 论文/研究 | arXiv 或原文链接 | 学术类内容必须可溯源 |
| 调查报告/人物专访 | 原文链接 | 非论文形式的长篇报道必须有原始出处 |
| 重大产品/工具 release | 官方 docs/blog/release 链接 | 需提供官方资料供读者深入了解 |

**补链流程（必须执行）**：

1. 若高价值条目缺第三方链接，读取 `~/.openclaw/skills/twitter-cli/SKILL.md`
2. 运行 `twitter tweet <tweet_id> --json` 补抓实际链接
3. 补抓后若仍无 repo/arXiv/官方链接：
   - 论文/研究报告类 → **排除**，不降为 related_links
   - 调查报告/专访类 → 在正文中注明"原文链接待补"，仍可保留
   - 重大产品 release → 在正文中注明"官方文档待补"，仍可保留

**禁止**：仅依赖 Twitter/X 源链接承载高价值内容；不得为回避链接要求而将论文/research 类条目伪装为纯观点类条目。

### 重点标注

对以下 item 标记 `is_highlight=true`。触发条件（满足任一即可）：

* likes > 5000 或 bookmarks > 3000

* 突破性技术/benchmark

* 关键人物发布的重要内容

* **行业重大事件（重磅调查报告、重要人物专访、重要政策发布）**

* 高影响力论文首发

* 重大产品/工具正式 release

**强制要求**：
- 每天 **至少 1 条 highlight**（若当天无符合条件条目则不强制）
- 调查报告、人物专访类条目若满足上述条件，**必须标记为 highlight**
- 不要滥用 highlight 标记；普通工具更新、日常版本迭代不应标记

## 链接规则

* 每条入选项都必须保留 1 条 X 主链接；默认使用对应帖子的 url，若 `_source_proxy=true` 且 `_canonical_url` 存在，则 X 主链接优先使用 `_canonical_url`

* 代表帖、quoted root、`_related_urls` 可以作为补充讨论链接，但不能替代 X 主链接本身

* `follow-up` 场景下，root/source X 链接优先讲事件本体；`_related_urls` 中当天新增的作者自回复或代表讨论帖用于说明"今天新增了什么"

* **链接优先级**：`_strong_links` > `_related_urls` > `_external_links` / `links`

  * 若 `_strong_links` 非空，必须保留 1-3 条；这是入稿的硬条件，不可跳过

  * `_related_urls` 作为讨论帖补充链接，在 `_strong_links` 已占据 3 条时不再追加；若有空位（不足 3 条）可追加 `_related_urls` 中的高互动讨论帖

  * 当 `_related_urls` 里同时存在作者自回复和普通讨论帖时，优先作者自回复；这通常是正文延续、补链或补媒体的入口

  * 第三方链接优先级：GitHub/release > arXiv/paper > HuggingFace/model/demo > 官方 docs/blog/changelog/release > 其他高质量原始资料

* 链接文本要具体：作者名 + 内容摘要，或 `GitHub: repo` / `arXiv: paper` / `Official: docs`；不要写「主链接/相关」

* 单条最多保留 1 条 X 主链接 + 1-3 条最强第三方链接（`_strong_links`）；第一条链接必须是 X 主链接；第三方链接不得为空（当条目有 `_strong_links` 时）

* 只能使用 item 自带的 `links`、`_strong_links`、`_external_links`、`_related_urls`，或通过 twitter-cli 补抓到的实际链接；不得臆造 URL

* 过滤掉广告跟踪、媒体二次报道、低信号聚合页；除非它本身就是官方首发页面
