# 编辑规则（完整版）

> 生成报告前必须阅读本文件。规则按主题组织，避免工作流调整后引用失效。

## 内容判断

脚本已做数值筛选，你只做内容判断。

### 从 strong 中排除

* 纯政治/社会话题（与 AI 无关）
* 纯自我宣传（播客推广、个人动态公告、直播预告、招聘）
* 明显泛鸡汤、生活方式或与开发者/AI 受众弱相关的内容
* 政治观点类内容（如 Trump 评论、Nazi 比较、政治攻击等），即使高互动也必须过滤

**重要例外**：关于 AI 公司领导人（Sam Altman、Demis Hassabis、Dario Amodei 等）的深度调查、人物专访、重要政策分析，即使涉及政治背景，只要核心内容是 AI 行业洞察且 likes > 5000，**必须选入**，不得以"政治相关"为由排除。Ronan Farrow、知名媒体对 OpenAI 的调查报道属于此类。

### 从 medium 和 backfill 中补充

* 首发论文、重大开源发布、模型/工具正式 release、行业重要政策
* 前一天发出、今天明显发酵成热点的高价值内容（如重要调查报告、人物专访）
* **当日最高互动量条目**（likes 最高的前 3 条），若符合 AI/开发生态主题且非纯自我宣传，必须入选

**特别注意**：当日 likes 最高的条目（如 > 20000 的 viral 事件）即使内容形式轻松（如视频 Demo、幽默讨论），只要核心与 AI 相关且非纯娱乐，必须入选。

## 去重与合并

### 同一事件判断标准

以 `_canonical_id` 或 `_canonical_url` 作为同一事件的主键；同一事件只能保留 1 条。

* 若源帖和代理帖都存在，优先源帖
* 若 `_source_proxy=true` 且 `_canonical_url` 存在，不要因为它是 quote/retweet 代理就直接丢弃
* 多人 quote/retweet 同一源帖时，合并为 1 条；主链接用 `_canonical_url`；讨论帖补充链接最多 1 条（在 `_strong_links` 已有 3 条时不追加）
* `likely_reply`、`quoted`、`_related_urls`、`_strong_links`、`_external_links` 都要用于合并判断

### 必须合并的情况

**事件链合并**：初始事件 → 后续影响/连锁反应 → 官方/社区回应 = 完整叙事链，合并为 1 条；主链接用首发帖，正文要点用分号串联各阶段进展。禁止拆分为多个独立条目。

**不同维度合并**：同一首发事件的技术根因分析、法律/版权分析、社区 fork/二次开发、官方回应等，均属同一事件的不同维度，合并为 1 条，主链接用首发帖。

### 不得合并的情况

独立但表面相似的事件（如不同组织同类型事件、同一话题不同研究团队的论文），必须分别独立成条。

### 同项目数量限制

同一项目当天最多出现 **2 次**，超出时必须合并，不得以"不同角度"为借口拆分。

### 合并判断决策树

1. 是否共享 `_canonical_id` 或 `_canonical_url`？ → 是：合并
2. 是否源自同一首发帖的二次讨论/分析/回应？ → 是：合并
3. 是否为同一事件链的不同阶段/连锁反应？ → 是：合并
4. 是否为不同主体/组织的独立事件，仅恰好同类或同天发生？ → 是：独立成条

## 历史去重

在最终生成 `post.json` 前，需要对 backfill 内容进行去重处理。

* 只有在今天出现明显更强的聚合传播数据，或新增有效信息时，才允许作为 follow-up 再次入选
* 新增有效信息包括：新的 repo/paper/release/官方回应等第三方资料链接；作者自回复中的正文延续；作者自回复或当天讨论帖里的信息性图片/视频；新 benchmark、新数据、新 release 说明
* backfill 最多 1-2 条

**标注格式**（必须在标题中标注，不得仅在要点或选题价值中提及）：

| 情况 | 标题格式 |
| --- | --- |
| 旧帖今日发酵（`_window=backfill`） | `「延迟发酵 {M月D日}」{原始标题}` |

**回填标签一致性**：若 `_window=backfill` 则标题必须标注「延迟发酵」；反之，若标题标注了「延迟发酵」则必须确认原帖来自 backfill。

## 分类列表

**固定分类**（优先使用，相同内容必须归入相同分类）：

* **模型发布**：新模型发布、模型更新、模型架构论文（✅ 包含新模型权重发布、模型版本更新、模型系列发布；❌ 不包含源码泄露归入安全事件、SDK/工具更新归入开发生态、非发布版本的评测/成本分析归入技术洞察）
* **开发生态**：开发工具、API、SDK、插件、AI coding agent 相关（✅ 包含 SDK 发布、工具链更新、开源项目重大里程碑；❌ 不包含纯模型发布、安全事件）
* **技术洞察**：深度技术分析、工程实践、benchmark、学术论文
* **产品动态**：产品功能更新、UI 更新、服务策略调整（非模型本身）

**动态分类**（仅在当天有特殊内容时启用）：安全事件、行业观点

**分类冲突优先级**：安全事件 > 模型发布 > 开发生态 > 技术洞察 > 产品动态

**禁止使用的分类名**：`开源生态`、`技术研究`、`安全研究`、`安全法律`、`工程突破`、`Dev Ecosystem`、`Model Releases`、`Technical Insights`、`Product Updates`

每类选 2-5 条，宁缺毋滥；当天高质量 fresh 很少时，不要拿低质量观点凑数；单个分类超过 5 条时必须将相似内容合并。

## 取舍优先级

* 默认目标 8-12 条；候选数 >= 8 时必须控制在 8-12 条；候选数 < 8 时可少于 8 条
* 优先级从高到低：首发论文/基准 > 官方 docs/blog/release > 开源 release/GitHub > 工程实证/成本研究 > 行业重大事件 > 高信息密度 thread > 纯观点/轻量 workflow

**互动数据参考阈值**：
* likes > 5000：强信号，除非内容明显不符主题，否则应入选
* likes 1000–5000：中等信号，需结合内容突破性价值综合判断；likes > 2500 的技术讨论优先入选
* likes 500–1000：弱信号，仅在首发论文/重大 release/首发 benchmark 时可入选
* likes < 500：需极强内容理由才入选（如官方首发 release、重大安全事件等）

**研究/工具/源码优先**：当研究/工具/源码条目与纯观点竞争时，优先前者；不要用观点贴挤掉 repo/paper/release。

**纯观点类条目限制**（最多 2 条，且必须同时满足）：
1. 来自关键人物（见关键人物库）或互动显著高（likes > 5000）
2. 附有原始资料链接（paper/repo/official doc），不得只有 X 帖链接

无实证的观点帖即使高互动也不选入主条目，可作为已入选条目的补充链接。

**禁止入选的内容**：
* 玩笑/表情包/纯 meme 类帖子（即使高互动），不得作为行业观点入选
* 内容为轻松幽默、与 AI 严肃讨论无关的 viral 帖子

***

## 弱内容排除（直接排除，不进入候选）

1. **官号自我宣传**：官方插件宣传、企业版/Pro 版差异化功能、招聘公告、直播预告、社区活动（**以下情况可入选**：全新能力发布、跨生态动态、Breaking Changes、安全/合规事件）
2. **数据较旧**：当天新数据极少时才选入前一天的内容，且需标注"延迟发酵"
3. **互动极低**：likes < 500 且 bookmarks < 50 的条目需严格审视
4. **重复事件**：同一事件多人讨论时合并为 1 条，优先选首发帖
5. **内容核实**：标题或摘要与原文不符的条目应排除；不得脑补内容
6. **弱相关**：纯 CLI 工具技巧、终端配置、SSH 运维、系统维护等话题，除非有明确的 AI/ML 生态影响
7. **推测表述为事实**：当原始帖使用"可能""疑似""或为"等模糊措辞时，本条目标题及要点不得将其改写为确定性结论

***

## 正文质量要求

* 每条正文必须达到 **80 字符以上**，提供充分背景与数据支撑
* 正文必须包含"why it matters"框架：解释为什么这条值得读者关注
* 正文必须引用**具体信源**：非 highlight 条目至少提及 1 个具体信源（如工程师/研究者账号、机构名称），highlight 条目正文需包含 2-3 个具体信源引用
* 论文/研究类条目：正文中的链接必须指向 arXiv/官方原文，不得仅引用社交媒体讨论
* 模型/工具 release 类条目：正文中的链接必须指向 GitHub/官方文档，不得仅引用社交媒体讨论

### 表述准确性要求

* 当事件分析基于推测而非官方确认时，必须保留原帖的模糊措辞（"或为""可能""据分析""疑似"）
* 禁止将社区推测、技术分析或二手解读表述为已确认事实
* 正文必须准确反映源帖的立场和情绪倾向，不得对内容进行反向解读

***

## 高价值条目第三方链接要求

| 条目类型 | 必须包含的第三方链接 | 缺少链接时的处理 |
| --- | --- | --- |
| 论文/研究 | arXiv 或原文链接 | **排除**，不降为 related_links |
| 调查报告/人物专访 | 原文链接（数值化 URL） | **排除**，不降为 related_links |
| 重大产品/工具 release | 官方 docs/blog/release 链接 | **排除**，不降为 related_links |

**补链优先级**：论文/研究类：arXiv > 官方 PDF > HuggingFace paper page；调查报告/专访类：原文官网链接 > 数值化 URL；产品/工具 release：GitHub release > 官方 docs/blog > changelog

**补链流程（必须在入选前完成）**：
1. 若高价值条目缺第三方链接，读取 `./twitter-cli.md`
2. 运行 `twitter tweet <tweet_id> --json` 补抓实际链接
3. 补抓后若仍无 repo/arXiv/官方链接：论文/调查报告/重大产品 release → **排除**

**禁止**：仅依赖 Twitter/X 源链接承载高价值内容；不得将论文/research 类条目伪装为纯观点类条目；不得以"正文注明待补"为由保留缺链条目；**不得臆造、猜测或推断 URL**

## 重点标注

对以下 item 标记 `is_highlight=true`（满足任一）：
* likes > 5000 或 bookmarks > 3000
* 突破性技术/benchmark
* 关键人物发布的重要内容
* **行业重大事件（重磅调查报告、重要人物专访、重要政策发布）**
* 高影响力论文首发
* 重大产品/工具正式 release

**强制要求**：每天 **至少 1 条 highlight**（若当天无符合条件条目则不强制）；调查报告、人物专访类条目若满足上述条件，**必须标记为 highlight**；不要滥用 highlight 标记。

***

## 链接规则

* 每条入选项都必须保留 1 条 X 主链接；若 `_source_proxy=true` 且 `_canonical_url` 存在，优先使用 `_canonical_url`
* **链接优先级**：`_strong_links` > `_related_urls` > `_external_links` / `links`
  * **必须保留**：若 `_strong_links` 非空，其中每个链接都必须体现在 `related_links` 中，不得遗漏
  * `_related_urls` 在 `_strong_links` 已占据 3 条时不再追加；若有空位可追加高互动讨论帖
  * 当 `_related_urls` 里同时存在作者自回复和普通讨论帖时，优先作者自回复
  * 第三方链接优先级：GitHub/release > arXiv/paper > HuggingFace/model/demo > 官方 docs/blog/changelog > 其他
* 链接文本要具体：作者名 + 内容摘要，或 `GitHub: repo` / `arXiv: paper` / `Official: docs`；不要写「主链接/相关」
* **正文中的第三方链接要求**：论文/研究类条目正文链接必须指向 arXiv/官方原文；模型/工具 release 类条目正文链接必须指向 GitHub/官方文档
* 单条最多保留 1 条 X 主链接 + 1-3 条最强第三方链接；第一条链接必须是 X 主链接
* 只能使用 item 自带的链接或通过 twitter-cli 补抓到的实际链接；**绝对禁止臆造 URL**
* 短链接（如 t.co）必须通过 WebFetch 展开验证，确认为有效页面后才可使用
* 过滤掉广告跟踪、媒体二次报道、低信号聚合页

## Writing Format Spec

### post.json 结构

```json
{
  "title": "{当日核心要点}【AI 资讯日报 {REPORT_DATE}】",
  "description": "每日 AI 领域精选资讯：{实际使用的分类列表}",
  "pubDate": "{REPORT_DATE}",
  "tags": ["AI", "资讯", "日报"],
  "slug": "ai-news-{REPORT_DATE}",
  "categories": [
    {
      "name": "开发生态",
      "items": [
        {
          "index": 1,
          "canonical_id": "原始 _canonical_id",
          "title": "中文标题（30 字以内）",
          "link": "https://x.com/.../status/...",
          "body": "中文正文...",
          "media": ["media/xxx.jpg"],
          "is_highlight": false,
          "related_links": [
            {"text": "GitHub: repo-name", "url": "https://github.com/..."}
          ]
        }
      ]
    }
  ]
}
```

### 每条 item 写作规则

**title**：必须中文，30 字以内，突出核心价值点；不得与原始推文标题相同。

**body**：必须中文正文，基于推文内容 + 补充信息生成。is_highlight 条目：3-4 段，充分展开背景、技术细节和意义；普通条目：1-2 段，说清"是什么、为什么值得关注"。互动数据口语化。不得原样复制英文推文内容。

**related_links**：从 `_strong_links` + 补充信息中的有效链接取；**必须包含 `_strong_links` 中的所有链接**；优先级：GitHub > arXiv > HuggingFace > 官方 docs > 其他；每条最多 3 个链接；只能使用实际存在的 URL，不得捏造。

**media**：is_highlight 条目从 Step 3 下载的图片相对路径数组（如 `media/12345_0.jpg`）；非 highlight 或下载失败则 `[]`。

### frontmatter

* `title`：从当日最重要的内容动态生成，格式 `{核心要点}【AI 资讯日报 {DATE}】`，不超过 50 字
* `description`：`"每日 AI 领域精选资讯：{实际使用的分类列表}"`
* `pubDate`：`REPORT_DATE`
* `tags`：`["AI", "资讯", "日报"]`
* `slug`：`"ai-news-{REPORT_DATE}"`

### 自检清单

写出 post.json 前逐条检查：

1. ✅ item 总数在 8-12 范围（候选充足时）
2. ✅ 每条 title 是中文，且不是原始推文标题的直拷
3. ✅ 每条 body 是中文正文，不含重复段落
4. ✅ category 来自允许列表（模型发布、开发生态、技术洞察、产品动态、安全事件、行业观点）
5. ✅ 无 placeholder 文本（TODO、TBD、xxx、待补充）
6. ✅ related_links 中的 URL 不是捏造的
7. ✅ `_strong_links` 中的所有链接都体现在 related_links 中
8. ✅ canonical_id 字段已填写
9. ✅ backfill 条目标题已标注「延迟发酵」且 `_window=backfill` 一致
